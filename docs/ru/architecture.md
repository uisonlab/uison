# Архитектура

[English](../architecture.md) · **Русский**

Эта страница объясняет, как устроен uison: что на входе, что на выходе, какая часть за что отвечает и почему в центре всего — JSON. Здесь же — две вещи, которые следуют из такого устройства: **консольный режим**, в котором вместо окна программа обменивается JSON-сообщениями, и **SSH-плеер**, который показывает программу, работающую на другой машине.

## Идея одной картинкой

```text
 экран: JSON-файл, Rust DSL, виджеты C++, UISON_JSON в C        данные     обработчики на Rust / C / C++
        │                                                         │                ▲
        ▼                                                         ▼                │ действия по имени
 ┌──────────────────────────────────────────────────────────────────────────────────┴───┐
 │ uison-ui: шаблоны, параметры, токены темы, привязки, раскладка, состояние элементов │
 └──────────────────────────────────────────────────────────────────────────────────────┘
        │  кадр примитивов (JSON-текст): rect, line, circle, tri, poly, text, image, clip, hit
        ▼
 ┌──────────────────────────────────────────────────────────────────────────────────────┐
 │ uison-frame: разбор, границы, diff с прошлым кадром → области повреждения, hit-test  │
 └──────────────────────────────────────────────────────────────────────────────────────┘
        │  перерисовать только повреждённое                     ▲ события (мышь, клавиши, касания, размер…)
        ▼                                                         │
 бэкенд: AppKit · UIKit · Win32 + Direct2D · Wayland/X11 + Cairo · Android Canvas · canvas 2D
```

По конвейеру идут два вида JSON:

- **Экран** — сложный JSON: компоненты с параметрами (`$title`), привязки к данным (`@inbox.count`), интерполяция (`"{@n} unread"`), токены темы (`$theme.accent`), списки, селекторы, имена действий. Его пишет человек (или он получается из Rust DSL и виджетов C++).
- **Кадр** — примитивный JSON: прямоугольники в абсолютных координатах, линии, круги, многоугольники, однострочный текст, картинки, группы `clip` и невидимые области `hit`. Его пишет программа, рисует бэкенд.

Всё между ними — обычный Rust: в JSON нет кода, в бэкендах нет раскладки и стилей.

## Почему JSON

JSON здесь — договор между слоями, а не просто формат настроек:

- **Один язык для всех языков программы.** Экран, написанный один раз, работает из Rust, C и C++: C и C++ передают через C ABI только строки и функции обратного вызова. Rust DSL и виджеты C++ генерируются из одной схемы (`uison-gen`), поэтому все три описывают одно и то же дерево.
- **Кадр — просто данные.** `App::frame` и `App::on_event` возвращают кадр строкой `String`. Бэкендом может управлять всё, что умеет печатать JSON: программа на C со `snprintf` ([урок 9](c/lessons/09-frame.md)), тест или другой процесс.
- **У всего, что пересекает границу, есть JSON-форма.** События (`{"type":"down","x":10,"y":20,"button":"left"}`), сообщения экрану (`{"action":"remove","key":"del-1"}`, `{"data":{"filter":"done"}}`) и запросы к платформе (`{"host":"copy","text":"…"}`) имеют одну каноническую текстовую форму ([события](screens/events.md)). Её же используют C API, сценарии проверки, консольный режим и плееры.
- **Всё видно глазами.** Кадр можно сохранить, сравнить, воспроизвести и прочитать. Сценарий — JSON-список шагов.
- **Без зависимостей.** У uison свой JSON (`uison-json`): pull-парсер с точным разбором чисел, строками без копирования и ошибками `строка:столбец`; изменяемое дерево `Value`; запись; `compact`, который переводит расширенный JSON (комментарии, висячие запятые, ключи без кавычек) в строгий одной строкой.

JSON остаётся **на границах**. Внутри процесса всё типизировано: бэкенд переводит событие системы в `Event`, `uison-frame` разбирает текст кадра в структуры один раз на кадр, бэкенд рисует по этим структурам через трейт `Canvas`. Перевод события в JSON и обратно стоит около 0,2 мкс.

## Слои и крейты

```text
 uison-json ──▶ uison-core ──▶ uison-frame ──▶ uison-ui ──▶ uison (зонтичный: prelude, run, run_console)
                    │              │               │
                    ▼              ▼               ▼
        uison-apple → uison-macos, uison-ios        uison-c (C API: uison.h, uison_kit.h, uison.hpp)
        uison-windows · uison-linux · uison-android · uison-web
```

| слой | крейт | что делает |
|---|---|---|
| данные | `uison-json` | разбор и запись JSON, `Value`, `compact` |
| договор | `uison-core` | геометрия, `Color`, `Font`, трейты `Canvas` и `TextMeasure`, `Host` (метрики текста и запросы к системе), `Event`, трейт `App`, размеры картинок, часы |
| кадр | `uison-frame` | `Frame::parse`, `diff` → `Damage`, `hit_test`, `paint` на любой `Canvas`, `Writer` (быстрый вывод кадра), `Runtime` (приложение + текущий кадр), событие ↔ JSON, исполнитель сценариев, консольный режим |
| экраны | `uison-ui` | компилятор экранов и рантайм `Ui` (это `App`), библиотека элементов `lib/*.json`, темы, Rust DSL |
| платформы | `uison-macos`, `uison-ios` (поверх `uison-apple`), `uison-windows`, `uison-linux`, `uison-android`, `uison-web` | окно, события, рисование, измерение текста |
| языки | `uison`, `uison-derive`, `uison-c`, `uison-gen` | вход для Rust, `#[derive(Data)]`, C/C++ API и пакеты, генерация обёрток |
| инструменты | `uison-player`, `uison-ssh-player` | плееры консольного режима (ниже) |

Всё, кроме `uison-ssh-player`, зависит только от `std`. Системные API вызываются через FFI, написанный вручную: рантайм Objective-C, CoreGraphics и CoreText; COM для Direct2D и DirectWrite; протокол Wayland и libxcb, Cairo и Pango через `dlopen`; JNI; импорты из маленького JavaScript-файла в браузере.

## Договор ядра

Приложение — всё, что реализует небольшой трейт из `uison-core`:

```rust
pub trait App {
    fn frame(&mut self, host: &dyn Host) -> String;                     // первый кадр
    fn on_event(&mut self, event: &Event, hit: Option<&str>, host: &dyn Host) -> Option<String>;
    fn wants_tick(&self) -> Option<Duration> { None }                    // таймеры, анимация
    fn set_waker(&mut self, _wake: Waker) {}                             // другие потоки → Event::Wake
    fn wants_keyboard(&self) -> Option<Keyboard> { None }                // экранная клавиатура
}
```

`hit` — `id` верхней области `hit` под указателем, найденной в прошлом кадре. `None` из `on_event` — «ничего не изменилось». `Host` — платформа глазами приложения: измерение текста, модификаторы, буфер обмена, открыть ссылку, системный выбор файла, размеры картинок.

`Ui` из `uison-ui` — одно из таких `App`. Программа может реализовать `App` и сама, со своими кадрами.

## Кадр

```json
{ "size": [400, 300], "background": "#F5F5F7", "items": [
  { "rect": [10, 10, 380, 230], "radius": 10, "fill": "#FFFFFF", "stroke": "#D2D2D7", "width": 1 },
  { "circle": [120, 80, 8], "fill": "#007AFF" },
  { "clip": [10, 10, 380, 230], "items": [
    { "text": "Dots: 1", "at": [170, 258], "size": 13, "color": "#86868B" } ] },
  { "hit": [290, 250, 100, 32], "id": "clear", "cursor": "pointer" }
] }
```

### Девять примитивов

Всё, что показывает любой экран, собрано из девяти видов элементов. У каждого элемента ровно один из ключей ниже, его значение — геометрия. Все девять реализованы в каждом бэкенде (macOS, iOS, Windows, Linux, Android, браузер) через трейт `Canvas`, и у любого элемента может быть `id`.

| ключ JSON | геометрия | остальные ключи | чем рисуется |
|---|---|---|---|
| `rect` | `[x, y, w, h]` | `fill`, `stroke`, `width` (обводка, по умолчанию 1), `radius` (скругление углов) | `Canvas::rect` |
| `line` | `[x1, y1, x2, y2]` | `color` (по умолчанию чёрный), `width`, `cap`: `"butt"` (по умолчанию) или `"round"` | `Canvas::line` |
| `circle` | `[cx, cy, r]` | `fill`, `stroke`, `width` | `Canvas::circle` |
| `tri` | `[x1, y1, x2, y2, x3, y3]` | `fill`, `stroke`, `width` | `Canvas::triangle` (по умолчанию — многоугольник) |
| `poly` | `[[x, y], [x, y], …]`, замкнутый | `fill`, `stroke`, `width`; заливка по правилу nonzero, скруглённые стыки | `Canvas::poly` |
| `text` | `"одна строка текста"` | `at: [x, y]` (левый верх, обязателен), `size` (по умолчанию 13), `color`, `font` (семейство или `monospace` / `serif` / `sans-serif`), `bold`, `italic` | `Canvas::text` |
| `image` | `[x, y, w, h]` | `src` (файл или имя `mem:`, обязателен), `fit`: `"cover"` (по умолчанию), `"contain"`, `"fill"`; `radius` | `Canvas::image` |
| `clip` | `[x, y, w, h]` | `items`: вложенные элементы, обрезанные по прямоугольнику | `Canvas::push_clip` / `pop_clip` |
| `hit` | `[x, y, w, h]` | `id` (его `on_event` получает как `hit`), `cursor`: `"arrow"`, `"pointer"`, `"text"` | не рисуется: hit-test и курсоры |

Фигурам нужен `fill`, `stroke` или оба; цвета — `"#RGB"`, `"#RRGGBB"` или `"#RRGGBBAA"`. Неизвестный ключ, ключ не от этой фигуры или повтор — ошибка со `строка:столбец`. Парсер не пропускает их молча, поэтому опечатка в кадре находится сразу.

- Координаты — логические точки, начало — левый верхний угол. Текст — одна строка, `at` — её левый верхний угол; перенос делает слой экранов.
- `uison-frame` разбирает кадр и считает границы (текст меряется через `TextMeasure`, поэтому границы точные).
- **Diff.** Новый кадр выравнивается с прошлым поэлементно (наибольшая общая подпоследовательность; группы `clip` с одинаковым прямоугольником сопоставляются и сравниваются внутри). Изменённые, добавленные и удалённые элементы дают области повреждения — бэкенд перерисовывает только их. На iOS и Android система всё равно просит всю view, поэтому там кадр рисуется целиком: полный кадр Studio на телефоне — 0,4–0,7 мс.
- **Hit-test и курсоры** берутся из областей `hit` — бэкенду не нужно ничего знать об элементах.
- Тонкие линии выравниваются по физическим пикселям одинаково во всех бэкендах.

## Слой экранов (`uison-ui`)

`Ui` хранит экран, данные, состояние элементов и обработчики. При каждом изменении он заново строит кадр:

1. **Раскрытие** — компоненты библиотеки (`Button`, `TextField`, `Tabs`…) и свои раскрываются с параметрами; `For` и `List` повторяют шаблоны по данным (`List` — виртуализированный).
2. **Привязка** — значения `@path`, интерполяция `{@path}`, локальное состояние `@~name`, селекторы (`{state: {…}}`, `{switch, cases}`), функции (`eq`, `ratio`, `pick`…) и токены темы вычисляются по данным, окружению (`@env.width`, `@env.dark`, `@env.safe.top`…) и теме.
3. **Раскладка** — модель в духе Flutter: `Row`, `Column`, `Stack`, `Wrap`, `Flow` (строчный текст со ссылками), `flex`, выравнивание, прокрутка, перенос текста.
4. **Вывод** — примитивы пишет `Writer`; то, что вне видимой части прокрутки, ничего не выводит.

Рантайм ведёт наведение, нажатие, фокус, каретку и выделение текста, прокрутку с инерцией и отскоком, различает тап и прокрутку на сенсорном экране, показывает подсказки и контекстные меню, обрабатывает горячие клавиши. Событие, важное приложению, вызывает **действие по имени**: `on: { click: "remove" }` в экране, `ui.on("remove", |cx| …)` в Rust (в C и C++ — функция или лямбда). Обработчик меняет данные или дерево; следующий кадр показывает изменение.

## Бэкенды

Бэкенд маленький, потому что всё перечисленное — общее. Он даёт:

- `run(app, title)` — окно и цикл событий;
- события системы → `Event` (мышь, колесо, касания, клавиши и ввод текста, размер, безопасная зона, тема, вставка);
- реализацию `Canvas` и `TextMeasure` с кешем строк текста в двух поколениях;
- после каждого события — проверку `wants_tick` (20 мс и меньше — тики по кадрам экрана: CADisplayLink, Choreographer, `WaitForVBlank`, frame callback Wayland; дольше — таймер) и `wants_keyboard`.

| платформа | окно и ввод | рисование и текст |
|---|---|---|
| macOS | AppKit, подкласс `NSView`, зарегистрированный в рантайме | CoreGraphics, CoreText |
| iOS | UIKit, `UIKeyInput`, CADisplayLink | CoreGraphics, CoreText |
| Windows | Win32, per-monitor DPI v2, `WM_POINTER` | Direct2D, DirectWrite, WIC |
| Linux | Wayland (свой код протокола) и X11 (libxcb), xkbcommon, свой клиент D-Bus для темы | Cairo, Pango — всё через `dlopen` |
| Android | Java-активность и view на ~300 строк, JNI | `android.graphics.Canvas` |
| браузер | WebAssembly без wasm-bindgen | canvas 2D |

Во всех бэкендах работают одни и те же переменные окружения для проверки программы без человека: `UISON_SCRIPT` (сценарий тапов, ввода, прокрутки по `key` элементов), `UISON_CAPTURE` (снимки), `UISON_HITMAP` (карта областей `hit`, чтобы водить настоящей мышью), `UISON_STATS`, `UISON_FLASH`, `UISON_RELOAD` (перезагрузка файлов экрана при сохранении, для отладки).

## Языки

- **Rust** — `uison::prelude`: `Ui`, DSL (`column`, `button`, `.on_click(|cx| …)`), `#[derive(Data)]` для структур ↔ данных, `source!` для файлов экрана.
- **C** — `uison.h` (C99) поверх статической или динамической `libuison`; `uison_kit.h` добавляет `UISON_JSON({…})` для экранов прямо в коде и таблицы полей для структур.
- **C++** — `uison.hpp` (RAII, лямбды, рефлексия структур без макросов) и `uison_widgets.hpp` (виджеты C++20 в духе Flutter, генерируются из схемы).

Все три приходят к одному `Ui` и одним бэкендам. Сообщение из другого потока (`post`) будит поток интерфейса через `Waker`.

## Консольный режим: JSON вместо окна

Раз весь выход приложения — кадр в JSON, а весь вход — события, у которых есть JSON-форма, окно становится необязательным. В **консольном режиме** у программы нет окна: она пишет кадры в stdout и читает события из stdin, по одному сообщению в строке.

```rust
if std::env::args().any(|a| a == "--console") {
    uison::run_console(app(), "My app");  // то же приложение, без окна
}
uison::run(app(), "My app");
```

```text
 программа (любой App)                               тот, кто на другом конце
┌───────────────────────────────┐   stdout   ┌──────────────────────────────────────┐
│ uison_frame::console::serve   │ ─────────▶ │ {"uison":0,"title":"Disk Usage"}     │
│  поток чтения → канал →       │            │ {"frame":{"size":[…],"items":[…]}}   │
│  on_event → кадр → строка     │            │ {"host":"copy","text":"…"}           │
│  таймеры, анимация, потоки    │   stdin    │                                      │
│  остаются в программе         │ ◀───────── │ {"type":"resize","w":1280,"h":796}   │
│                               │            │ {"type":"down","x":412,"y":230,…}    │
└───────────────────────────────┘            │ {"action":"rescan"}                  │
                                             └──────────────────────────────────────┘
```

Как это устроено:

- `uison_frame::console::serve` — цикл, который ничего не знает об `Ui`: поток читает строки в канал; главный цикл ждёт строку или срок `wants_tick`, делает hit-test по последнему кадру, вызывает `on_event` и пишет новый кадр строгим JSON в одну строку (`compact`, числа не переформатируются). Каждое сообщение — одна запись `write_all`.
- Запросы `Host` становятся сообщениями: копирование, открытие ссылки и вставка уходят на другую сторону как `{"host":…}`; ответ на вставку возвращается событием `paste`.
- stdout принадлежит протоколу. На macOS и Linux протокол пишет в копию дескриптора 1, а сам дескриптор 1 направлен в stderr, — случайный `println!` поток не сломает.
- Текст по-прежнему меряет программа. На машине без шрифтов (Linux-сервер без Cairo и Pango) или с `UISON_TEXT=estimate` она оценивает ширины по типичным ширинам символов шрифта без засечек и сообщает об этом в stderr; плеер рисует кадр своими шрифтами.
- Программа выходит, когда stdin закрыт.

С такой программой можно говорить одной оболочкой:

```sh
printf '%s\n' '{"type":"resize","w":900,"h":600}' '{"action":"about"}' \
  | target/release/disk-usage --console | cut -c1-120
```

Так любая программа на uison становится тем, что можно проверять трубами, записывать потоком строк, вести из другой программы или показывать в другом месте. Протокол целиком — на [странице консольного режима](console.md).

## Плееры

**Плеер** — обычная программа на uison, которая запускает другую программу в консольном режиме и показывает её.

- **`uison-player`** (локальный) запускает программу дочерним процессом. Вкладка **App** встраивает кадры программы в свой (`Writer::frame` сдвигает их на место и добавляет префикс к id областей `hit`, чтобы области программы и плеера не путались), передаёт мышь и клавиши над областью программы, отправляет `resize` и тему системы. Вкладка **JSON** — все сообщения в обе стороны вместе с stderr, фильтры и поле, чтобы отправить свою строку. В строке состояния — трафик, кадры в секунду и задержка. `uison-player` — ещё и библиотека: способ достучаться до программы — трейт `Link`, стартовый экран — заменяемый компонент `Launcher`.
- **`uison-ssh-player`** — та же библиотека с SSH-каналом. Он подключается к серверу (ключ или пароль), проверяет ключ хоста по `~/.ssh/known_hosts` и своему списку (новый хост запоминается с отпечатком, сменившийся ключ — отказ), по желанию загружает программу (`mkdir -p … && cat > путь && chmod +x путь` — без SFTP, на сервер ничего не ставится) и запускает её с `--console`. Соединение живёт между запусками; **Stop** останавливает программу, соединение остаётся.

```text
 uison-ssh-player                           сервер: любой sshd, ничего не установлено
┌──────────────────────────┐      SSH       ┌────────────────────────────────────┐
│ 1. подключиться, ключ    │ ─────────────▶ │ ключ или пароль                    │
│    хоста                 │                │                                    │
│ 2. загрузить (по жел.)   │ ──── exec ───▶ │ cat > ~/uison/prog && chmod +x     │
│ 3. запустить             │ ──── exec ───▶ │ ~/uison/prog аргументы --console   │
│ вкладки App / JSON       │ ◀─── stdout ── │ кадры                              │
│                          │ ──── stdin ──▶ │ события, действия                  │
└──────────────────────────┘                └────────────────────────────────────┘
```

Библиотека SSH (russh с `ring` и tokio на одном потоке) — **единственная внешняя зависимость в репозитории**, и живёт она только в этом крейте: фреймворк и программа на сервере по-прежнему знают только stdin и stdout. Плеер работает и на телефоне (проверено на Android 16): **Choose key…** берёт ключ через системный выбор файла и хранит закрытую копию в папке приложения, **New key** создаёт ключ ed25519 на устройстве и показывает строку для `authorized_keys`, а программа, разложенная под компьютер, рисуется уменьшенной.

## Сколько это стоит

Замеры на Disk Usage по `/System/Library/Frameworks` (около 3000 секторов диаграммы):

| | |
|---|---|
| кадр с диаграммой | ~125 КБ JSON |
| программа на одно событие наведения | 1,7 мс (приложение 1,0, разбор своего кадра 0,4, `compact` 0,3) |
| событие → кадр обратно через локальную трубу | 1,85 мс (в обычном окне — 1,4 мс) |
| анимация приближения через трубу | ~55 кадров в секунду, 6–7 МБ/с |
| то же по SSH до облачного сервера | круг 40 мс; наведение → кадр 204 мс (медиана) |

Локально кадр на каждое изменение почти ничего не стоит. Через интернет медленнее всего — передача кадра целиком. Поэтому следующий шаг для удалённых окон — передавать **экран один раз, а потом изменения данных и действия**, с раскладкой и шрифтами на стороне того, кто смотрит, а не кадры.

## Правила устройства

- Только `std`; системные API — через FFI, написанный вручную. Размер бинарника важен (Studio, главное демо, — ~840 КБ на macOS и ~220 КБ WebAssembly в gzip), но не важнее качества.
- Логика — на языке программы, никогда в JSON: в JSON — данные, шаблоны, привязки и имена действий.
- Одна модель кадра для всех платформ: бэкенд рисует примитивы и сообщает о событиях — и это всё, что он знает.
- Каждый шаг проверяется автоматически: сценарии, снимки и карты областей во всех бэкендах; уроки ядра на трёх языках дают снимки, совпадающие до пикселя.
